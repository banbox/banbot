# Shared accounts and Hub

Default live entries for time-series, factor and mixed strategies use a local Hub account service. Robots own public inputs, strategy computation and order presentation. Hub owns account ledgers, private reports, net execution and pending/protection advancement. Stopping a robot does not close positions or stop its Hub account.

## Choose a run mode

| Goal | Configuration and command | Account location |
| --- | --- | --- |
| Historical backtest | `backtest`; weights/events for factors, events for mixed runs | In-process simulation |
| Factor/mixed historical paper replay | `trade --dry-run` | Historical events replay, without a live Hub account |
| Live simulation | `env: dry_run`; start `hub` before `trade` | Durable Hub paper account |
| Production trading | `env: prod`; start `hub` before `trade` | Durable Hub account, requiring verified real-session capabilities |

An omitted `execution.live_provider`, `hub` or `banexg` selects Hub. A missing Hub fails startup without local-sender fallback. Custom registered providers are explicit production embedding options and cannot mix with Hub in one robot. The retired `LiveOrderMgr` sender is not an alternative route around account execution.

### Embedded production time-series accounts always use the Hub order manager

An embedded production time-series robot (`env: prod` with a registered custom embedded `execution.live_provider`, i.e. not omitted and not `banexg`/`hub`; also the time-series account of a mixed robot) always uses the same Hub order manager as a default Hub robot, with the Hub living inside the robot process: it wraps the robot's own shared account, starts no socket or market stream, and never closes that account. There is no facade switch and no way back to the old shared facade (`SharedOrderMgr` is backtest-only; live and dry-run accounts always use the Hub order manager, including the time-series part of a mixed factor + time-series account, whose factor part keeps using the same account and is never given a reused quote observed before its executable time; under the default socket Hub, the time-series part of a mixed account also goes through the Hub robot bridge).

- The former `execution.ts_facade` key was removed. Any value under `execution` or `accounts.<account>` fails config loading with a message saying the shared facade was removed and the key must be deleted.
- Upgrading: an account that ran under the old shared facade has its legacy checkpoints imported automatically, once, on its first start (when the robot journal does not exist yet and the account holds active legacy orders: positions, stops, take-profit ladders, OCO groups, resting entries). The legacy data is left untouched. If an order cannot be mapped faithfully the whole import is refused and startup fails with the cause; nothing is written. Rolling back to the old facade is no longer available.
- `take_over_strat` (external position takeover) is supported.
- The robot journal is `<datadir>/execution/robots/ts-local-<hash>.json`, separate from a socket Hub robot's journal.
- The in-process Hub advances pending orders (entries and protections) once per second and only logs failures as warnings; freezing the account is still handled by the account's own report loop under its usual rule.

To run an account through the embedded path with the stock banexg capabilities, register `entry.NewBanexgLiveBinding` under a custom name (`entry.RegisterFactorLiveBinding("<name>", entry.NewBanexgLiveBinding)`) and set `execution.live_provider: <name>`. Embedded mode refuses a declared `leverage` (set it on the exchange). A relative `execution.store` is resolved against the directory of the config file that declares it. The embedded entry reuses a fetched quote of an instrument for 1 second (concurrent reads share one request, failures are not cached), and funding is recovered by the account's private report worker (on a cash mismatch, and at most every 5 minutes), not polled by the entry. Factor funding data sources poll once per minute for the whole account and retry after a transient exchange error.

## Configure and start

1. Prepare base market/database configuration and compiled strategies. The default Hub currently accepts only `prod`/`dry_run` linear perpetual accounts with an explicit settlement currency. Testnet, spot, inverse contracts and live options are unsupported.
2. Declare stable strategy `id`, `account` and same-account `capital_weight` values in robot configuration. Supply positive `wallet_amounts`, `execution.margin_rate` (greater than 0 and at most 1), `max_account_margin`, `max_virtual_gross` and `strategy_gross_limit`. Capital declarations do not deposit exchange funds or permit allocation beyond available account cash.
3. Configure `execution.instruments`, keyed by SID, with `id`, `version`, `valuation: linear_perpetual`, `settlement_currency`, `quantity_step`, `price_tick`, `contract_size`, `money_scale`, plus the minimum order size `min_steps` (a count of `quantity_step` units) and minimum notional `min_notional`. Time-series instrument IDs are canonical symbols; factor SIDMap entries must match their instruments. Units, versions and precision must match normalized banexg market metadata. Do not copy another instrument's values. Registration compares them with public market metadata: units and precision must match, and `min_steps` / `min_notional` must not be lower than the exchange requirement, otherwise startup is rejected.
4. Use the same absolute `execution.sender_lease_dir` on the host and every process capable of sending for the physical account. Production Hub requires explicit configuration. Locks in different directories do not prevent duplicate senders. Stop and migrate the old sender before cutover; do not run another owner alongside it.
5. Production robots supply account credentials and `funding_policy: required-stream`, passing capability and startup reconciliation checks. Live simulation supplies positive paper cash and `funding_policy: explicit-zero`. Hub does not currently ingest simulated funding; `required-stream` cannot substitute for that declaration. The default route does not establish complete parity with historical configurations.

6. The production account must be in one-way (net) position mode, and its API key must allow trading. Hub checks this when it registers a production account, before any order path exists: it refuses registration when trading is not permitted, when the balance or key-permission calls fail, or when the account is in hedge (dual-side) position mode. Withdrawals enabled on the key and a key without an IP restriction are only logged as warnings. If the venue does not report the position mode, a warning is logged and hedged venue positions are rejected later by the adapter. Dry-run accounts have no credentials and are not checked. A robot with embedded credentials (no Hub) runs the same startup check and refuses to start when it fails.

This is only a path overlay for an existing complete configuration. It omits strategies, instruments and risk declarations:

```yaml
env: dry_run
execution:
  live_provider: hub
  hub_socket: /ban/data/execution/hub.sock
  sender_lease_dir: /ban/sender-leases
  store: /ban/data/execution-declaration.sqlite
  funding_policy: explicit-zero
```

Time-series live preflight still requires `execution.store` and sender-lease declarations, also for `env: dry_run` (a missing one fails with `requires a durable live ledger`). The `hub` and `trade` configurations must both contain `time_start`, or startup is refused. Hub chooses the actual account database under `<datadir>/execution` by account identity; a robot cannot redirect the remote ledger with `store`. Put account overrides directly in `accounts.<name>`, for example `accounts.default.hub_socket`, without a nested execution block.

Hub configuration supplies database/public-market settings and the sender lease. Private account credentials arrive in robot registration requests. Hub does not initialize private accounts from its own YAML or give credentials to public miners. Arbitrary exchange SDK options are not inherited; old configurations relying on custom endpoints/proxies in those options require separate checking.

Check startup logs in the foreground first. Start the robot after Hub has successfully begun listening:

```sh
/ban/bot hub --datadir /ban/data --config /ban/hub.yml
# Start the robot in a second terminal
/ban/bot trade --datadir /ban/data --config /ban/live.yml
```

`spider` is a CLI alias for `hub`; do not start a second service on the same path. Public market data uses `spider_addr`, default `127.0.0.1:6789`. The private socket defaults to `<datadir>/execution/hub.sock`. To change it, use Hub's `--execution-socket /absolute/path` and the same robot `execution.hub_socket`. The Hub reads only the command-line flag, not `execution.hub_socket` in YAML (that is the robot-side setting); without the flag it falls back to `<datadir>/execution/hub.sock`, which can exceed the Unix socket path limit with a long data directory, so pass `--execution-socket` explicitly in production.

The private socket is a Unix domain socket whose path length is limited by the OS (about 104 bytes on macOS, 108 on Linux). When the data directory path is long, set `execution.hub_socket` / `--execution-socket` to a short absolute path such as `/ban/hub.sock`. The socket is mode 0600 and its directory must not be group/world writable. All clients under the same OS user are trusted to operate every registered account. There is no private TCP transport or strategy-level multi-user authorization; do not expose it as a remote account service.

## Multiple strategies and pending orders

One physical account should have one sending owner. TS/factor strategies retain separate budgets and virtual positions. Account execution nets opposing contributions and sends only the remainder. Exchange balances remain shared; use separate physical accounts for independent capital and risk boundaries. When one strategy closes a long lot and a short lot of the same instrument in one plan (for example "exit all", or a long take-profit and a short stop firing in the same tick), the two lots are closed internally at the same price and no exchange order is sent; other opposite intents of the same strategy (opening both directions, flips) are not crossed internally.

First registration establishes account capital, risk and instrument baselines. Later robots can add strategies only from unassigned cash, without replacing the baseline or dynamically adding instruments not installed by the host. Preserve account/strategy IDs, declarations and local journals across restart. Renaming cannot bypass recovery; two writers using the same journal encounter file-lock/epoch conflicts.

Account-owned pending orders and protection continue when the originating robot disconnects. Software protection needs a running Hub and visible quotes. Execution uses independent REST book snapshots and cannot guarantee detection of transient crossings between snapshots. Native protection also requires explicit adapter capability evidence. `cancel_entry` cancels remaining entry without closing filled inventory; closing is a separate exit request. Command acceptance, a cancellation response or a robot display update cannot replace final fill/cancellation evidence. Callbacks may also be delivered more than once.

## Operation and troubleshooting

**Simulated costs in dry_run.** A pure time-series account takes its simulated fee from `exchange.<name>.fees.<market>.taker` and charges every fill at that rate; when it is not configured the fee is zero and a warning is logged at startup. Fills use the live best bid/ask (buys at the ask, sells at the bid) with no additional slippage. Accounts that include factor strategies use the strategies' own `fee_rate` / `slippage_rate`. Simulated costs are part of the dry_run account registration: after changing the fee rate an existing dry_run ledger refuses to start because the registration no longer matches, and the account's dry_run ledger (its directory under `execution/` in the data directory) must be cleared to start over.

- **Clock**: every account quote read (market stream, embedded quotes, default limit pricing) tolerates a host clock up to 1 second behind the exchange, observing such a book at receipt time; further behind, order books are refused, account registration fails, and the Hub log shows `invalid or stale account depth timestamp`. Keep the Hub and robot hosts synchronised (for example with NTP).
- **Generic robot error**: when a robot reports `hub operation failed; inspect account recovery state before retrying`, the reason (which may contain credential details, so it is not sent back) is only written to the Hub process log as `hub operation failed operation=... error=...`. Read the Hub log, not the robot output.
- **Entry size and venue minimum**: the robot converts a strategy entry request into order steps. An explicit quantity (`Amount`) is used first; otherwise the cost `LegalCost`; if neither is set, cost = strategy capital x stake fraction x `CostRate` (1 when unset). The stake fraction is `stake_pct / 100`; when `stake_pct` is 0 it is `stake_amount / strategy capital`, where strategy capital is the account initial NAV times the strategy's `capital_weight`. The cost is then divided by quantity step x contract size x reference price and rounded down to steps. An entry below `min_steps` or `min_notional`, or above the strategy's `strategy_gross_limit`, is dropped; the robot logs the warning `entry rejected: size below the tradable minimum or above the strategy allowance` and keeps running. When you see it, increase `stake_pct`/`stake_amount`, the strategy capital or the requested cost. A netted difference that falls below the venue minimum at the Hub is refused and dropped the same way, and is never resent.
- **When an entry is refused**: on the default Hub path, a new entry refused by the account owner (limit price not on the price tick, strategy or account exposure/margin budget exceeded, short on a spot instrument, opening or flipping in opposite directions within one strategy in the same plan, the account not being ready (`account_not_ready`), or a stale entry signal (`stale_entry`)) is dropped with the warning `hub rejected an entry; it is dropped, not retried`. The robot keeps running, the account is not frozen by a refused entry, and the entry does not use up the bar's open-order capacity. For grids and multi-lot strategies, an opposite entry of the same strategy may be placed one tick later than a stop (a reduction), which always executes first. An already accepted, still pending entry that the account later refuses while advancing on its own is ended by the owner (the refusal reason is audited) instead of freezing the account. Refused exits, edits and protection changes are not dropped; they still stop the robot with an error so that no position is left unmanaged.
- **Account not ready and transient outages**: when the private report worker hits a transient read failure (network failure, timeout, rate limit, temporary ban, venue overload, indeterminate result, or account depth not yet visible/stale), it neither freezes the account nor stops: the tick is skipped and the account is unready until recovery, so new entries are dropped with `account_not_ready` while the robot keeps running. The Hub logs a WARN at the start, an ERROR if it persists beyond 1 minute and an INFO on recovery; a rate limit pauses periodic and account-change reconciliation for the venue's Retry-After (default 30 s). Every other error still freezes the account and logs an ERROR `account frozen by the private report worker` with the reason and error. A genuine cash difference (for example an external transfer) also freezes.
- **Stale entry signals**: when the signal time of a time-series entry is older than max(2 x timeframe, 2 minutes), the account owner refuses it with `stale_entry` (the robot drops it and continues); an already accepted command still replays idempotently. On restart the robot logs an INFO `hub resends a frozen command` for each frozen command it resends.
- **Reconciliation and request weight**: the full account snapshot (balance, positions, all open and conditional orders) runs every 30 seconds, sooner on an account-change push, an order report or a transient outage; the 5-second ticks in between only advance pending orders. Funding is no longer fetched every 5 seconds: it is fetched on demand when reconciliation finds a settled cash difference (then reconciled once more), otherwise at most every 5 minutes. The account market stream requests 5 depth levels for both REST snapshots and the websocket subscription, spaces REST snapshots at least min(TTL/4, 1 second) apart per instrument, and falls back to the SDK default depth when the venue reports the limit as invalid. Measured on Binance, the request weight of one account with two instruments dropped from about 1600/min to about 450/min (IP limit 2400/min, shared by every process on the host); leave headroom when other processes run on the same host.
- **Registration fails with `hedged position outside linear net contract`**: the account really is in hedge (dual-side) mode; switch it to one-way mode. Builds on banexg v0.2.67 or older also reported Binance one-way positions as hedged, so such builds refuse a restart with an open position; current builds use banexg v0.2.68, which fixes this.
- **`execution.instruments` keys must be the symbol's real SID in the database**: a wrong key stops the robot with `kline ingress emitted foreign source/SID`; use the symbol's ID in the database `exsymbol` table.
- **Dashboard**: time-series, factor and mixed robots start the Dashboard only when `api_server.enable: true` is set and the robot has exactly one account; with several accounts it is not started and a warning is logged. Requests need `X-Authorization: Bearer <token>` and `X-Account`. Balance comes from the execution ledger as a single settlement-currency row. Hub robots hold no account credentials, so raw exchange orders/positions/incomes and the trade-download endpoints are refused, and `/close_exg_pos` is refused too; close through the strategy orders instead.
- **Configuration with no effect**: `pairlists` (when it would have selected pairs), `pairmgr.cron`, `min_open_rate`, `charge_on_bomb`, `margin_add_rate`, `put_limit_secs`, `odbook_ttl`, `account_pull_secs` and `bt_in_live` are ignored with one startup warning each; `--out` is rejected; pairs are fixed at startup, so dynamic `UpdatePairs` and `pairlists`/`pairmgr` rotation are unavailable. Details: [Configuration](./configuration.md) and the [live capability support matrix](./live_trading.md#live-capability-support-matrix).
- **Notifications**: see [Notifications](./notifications.md); messages are queued asynchronously and the maintenance jobs that need the legacy wallet (pair rotation, balance polling, trigger-order verification, wallet snapshots) are not run.
- **Stopping**: both `hub` and `trade` stop on SIGINT/SIGTERM (Ctrl-C or `kill`); the Hub removes its socket on exit. The reason a robot ended is logged as `time-series robot stopping: ...`.

## Restart and recovery

- **Robot-only restart:** leave Hub and its account running, and reconnect with the original configuration and journal. Account reports, public clocks and pending protection remain active. Client disconnect does not remove an account or close positions.
- **Hub restart:** preserve the whole execution directory (one subdirectory per account, containing the host declaration `host-declaration-v1.json`), SQLite files (including WAL sidecars), paper journals and robot journals. `accounts.json` stores credential-free identities only. Recovered accounts enter `waiting_authentication`, with local protection inactive. A robot must register again; account operation resumes only after recovery and reconciliation succeed. There is no autonomous credential restoration guarantee when all robots are offline.
- **Paper recovery:** registration restores simulated orders, cash and costs. Missing/corrupt journals or changed initial cash, fees, slippage/model fail recovery. Do not delete the ledger to bypass a conflict.
- **Stale socket:** verify the old Hub has stopped and released sender ownership before handling its stale path. Startup does not automatically delete an existing socket or take over its owner.

Ambiguous submission/cancellation outcomes retain states such as `Unknown`/`CancelPending` and block ordinary position changes. Recover/retry with the original command ID and payload instead of inventing a replacement order. Require stable-client-ID queries, complete trade history and account reconciliation. One not-found response cannot prove zero execution. Report/recovery failures can persistently freeze an account; do not edit SQLite order states or remove dedup records.

If a late fill arrives after `Rejected`, no supported operator command can reopen that order, and repeated restarts cannot repair it. Stop new strategy submissions and all account senders, wait for them to exit, then preserve the database/WAL, redacted logs and order/trade evidence for an audited maintainer repair. Keep the freeze; do not resubmit or book the same fill as both an external position and strategy fill. An interrupted accepted policy-entry cancellation also lacks a general operator completion tool; report it and retain evidence.

Stopping Hub stops and joins account work. Check real positions, working orders and protection arrangements first. Paper runs and unit tests establish software contracts; they do not establish real-venue readiness, profitability, capacity or slippage acceptance.
